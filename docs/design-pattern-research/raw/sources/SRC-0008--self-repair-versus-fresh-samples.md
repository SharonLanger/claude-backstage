## Reader's orientation

A coding model that can turn some failing programs into passing ones still needs to beat the alternatives available at the same generation budget. Olausson et al. compare drawing new answers to a fixed Python problem with drawing initial answers and spending some of the budget on revisions guided by a test failure and a diagnosis. Under the headline program-count measure, the better allocation depends on the model, benchmark and budget. Giving repair more distinct starting draws and fewer revisions per draw often helps relative to a fresh-only baseline. The study also changes who writes the diagnosis and finds substantial gains in some conditions. Executable benchmark tests make the outcome observable. Workflow speed, review quality and the best way to select among multiple plausible repository changes remain open questions. [Conference PDF, §§1, 3–5, Figs. 3–5 and Table 1](https://proceedings.iclr.cc/paper_files/paper/2024/file/9ddc141bdbf9d1db510cefff56c586ad-Paper-Conference.pdf#page=4)

## Detailed analytical reading

### What the system can observe and what it counts as success

The initial model sees a task specification and generates `n_p` candidate solutions independently under the sampling protocol. The evaluator executes them on the task's test bed. Any candidate passing the entire suite is enough to end the search. If the batch fails, the repair stage gets the original task, a failing program and execution evidence such as an error or a concrete input-output mismatch. A diagnosis produced from those inputs supplies an additional signal to the repair generator. The same programming model handles initial generation and repair. For same-model self-repair, the diagnosis and repaired code are generated together in one completion. For different-model feedback, the diagnosis is a separate completion that the programming model receives when it generates a repair. All repairs associated with one initial candidate descend from that candidate. Ten repair samples on the same failure are sibling alternatives, each starting from that program. [Conference PDF, Fig. 1, §3.1, Fig. 2 and App. G](https://proceedings.iclr.cc/paper_files/paper/2024/file/9ddc141bdbf9d1db510cefff56c586ad-Paper-Conference.pdf#page=3)

The paper assumes access to the full executable suite. The system can use failure evidence from the same underlying test bed that determines success without a separate private correctness suite. The outcome counts a task as solved when a candidate passes every benchmark test. This is an existence measure with a test-based selection rule. There is no ranking contest among passing samples and no separate estimate of whether a developer or a judge model would choose a correct implementation when tests are incomplete. Appendix G describes the actual prompts: access to the test bed belongs to the evaluator, and the repair input includes observed execution feedback. [Conference PDF, §2, pp. 2–3 and §3.1, p. 3](https://proceedings.iclr.cc/paper_files/paper/2024/file/9ddc141bdbf9d1db510cefff56c586ad-Paper-Conference.pdf#page=3)

### The denominator for a fair comparison

For a fresh-only search, `pass@k` estimates the chance that at least one of `k` independent draws from the same model satisfies the tests. For repair, the authors compare one tree against a fresh-only budget equal to its maximum number of programs. With joint diagnosis and repair, this maximum is `n_p + n_p × n_fr`, where `n_fr` is the number of joint completions per initial candidate. With separate stages, it is `n_p + n_p × n_f × n_r`, where `n_f` counts diagnoses per initial program and `n_r` counts repairs per diagnosis. Feedback text adds no program to that count. When an initial program passes, the runtime tree can stop before spending its full allowance. The matched `k` measures candidate opportunities. A separate feedback call, longer prompts, output verbosity, inference prices and elapsed time can make equal values of `k` cost different amounts to deploy. [Conference PDF, §3.2, pp. 4–5 and App. A, p. 13](https://proceedings.iclr.cc/paper_files/paper/2024/file/9ddc141bdbf9d1db510cefff56c586ad-Paper-Conference.pdf#page=4)

The authors generated a reusable pool for each specification, starting with 50 initial programs, and estimated each configuration by averaging 1,000 subtrees drawn with replacement from that frozen pool. The pool has up to 25 diagnosis or joint diagnosis-repair samples per failing program in the standard setup and 10 feedback samples in §4.2. The fresh-only comparison ranges up to 50 samples. Reusing the pool makes a grid of comparisons feasible and introduces possible finite-pool artefacts acknowledged in §5. The plotted variability comes from the stated resampling procedure. A thousand bootstrap draws give no equivalent number of newly solved tasks or newly generated trees. [Conference PDF, §3.2, pp. 4–5, Fig. 5 and §5, p. 9](https://proceedings.iclr.cc/paper_files/paper/2024/file/9ddc141bdbf9d1db510cefff56c586ad-Paper-Conference.pdf#page=4)

Appendix A prices each configuration by its mean generated program and feedback tokens, including early stops, and reports mean success at that mean cost. Batched search generates the initial batch before checking success, then runs the repair batch if needed. Sequential search explores each initial solution and its repair branch before drawing another and can stop at the first passing program. Broad trends persist, with self-repair generally less favorable under the sequential accounting, especially where baseline pass rates are already high. For example, GPT-3.5 on APPS reaches 1.04 times its fresh baseline at 25 initial programs with one repair in the program-count heatmap. The batched and sequential token heatmaps contain no displayed cell above parity for that model and dataset. The sensitivity analysis measures output tokens. It does not price input tokens, test execution, human attention, or the wall-clock advantage of parallel scheduling. [Conference PDF, Fig. 3a, App. A and Figs. 6a and 9a, pp. 13–17](https://proceedings.iclr.cc/paper_files/paper/2024/file/9ddc141bdbf9d1db510cefff56c586ad-Paper-Conference.pdf#page=13)

### Where allocating more opportunities to fresh draws helped

The experiments used CodeLlama-13b-instruct and frozen `gpt-3.5-turbo-0301` and `gpt-4-0314` endpoints at temperature 0.8. The tasks come from HumanEval and a stratified random APPS test sample of 300 problems (60 introductory, 180 interview and 60 competition). Appendix G specifies that HumanEval initial generation is zero-shot, with a hand-built example for feedback, repair and joint feedback-repair based on a HumanEval problem. The analogous APPS prompts use train-set examples or specifications as described in G.1. The same-model experiment varies the initial batch across 1, 2, 5, 10 and 25, and joint feedback-repair samples per failing initial program across 1, 3, 5 and 10, reporting comparisons up to `k = 50`. Figures 3 and 4 show four model and benchmark pairings, and Figure 12 reports the other two. [Conference PDF, §4, p. 5 and Apps. B, G–H](https://proceedings.iclr.cc/paper_files/paper/2024/file/9ddc141bdbf9d1db510cefff56c586ad-Paper-Conference.pdf#page=5)

In the paper's GPT-4/APPS example, ten initial programs with one repair each pass at 66.1%, versus 63.1% for 20 fresh samples. Two initial programs with ten repairs each pass at 61.8%, versus 63.4% for 22 fresh samples. Each hybrid is matched to its own fresh baseline. The two hybrids have different budgets, and the numerical gains are +3.0 and −1.6 percentage points, respectively. Figure 3b rounds the corresponding ratios to 1.05 and 0.97. Small initial batches with many repairs commonly lose to fresh draws at their respective candidate budgets. For HumanEval, GPT-3.5 has little headroom, while CodeLlama shows larger relative gains in some configurations. On APPS, GPT-4 gains up to about 8% relative across the displayed aggregate comparisons, while the same-model GPT-3.5 and CodeLlama hybrids tend to trail or match fresh sampling outside some higher-budget configurations. [Conference PDF, §1, p. 2, §4.1 and Figs. 3–5, pp. 5–7, and App. B, Fig. 12](https://proceedings.iclr.cc/paper_files/paper/2024/file/9ddc141bdbf9d1db510cefff56c586ad-Paper-Conference.pdf#page=6)

The authors propose that a larger initial batch increases the chance of obtaining an implementation whose mistakes can be fixed. The experiment varies the number of draws and does not measure algorithmic diversity directly. Appendix C also shows that absolute ability to repair and advantage over fresh draws can move in different directions. For example, GPT-4's per-repair success in Table 2 is 28.8% on introductory APPS tasks and 8.6% on competition tasks, yet its best reported relative gains over fresh sampling are larger in the competition subset. The denominator in Table 2 is sampled repairs of failing programs, and the initial failure pool changes across model and difficulty groups. The authors suggest several possible determinants of the relative advantage, including how informative the tests are, ambiguity in the specification, and the relative odds of getting a correct fresh draw. [Conference PDF, §4.1, pp. 5–7 and App. C, Table 2 and Figs. 13–16, pp. 19–23](https://proceedings.iclr.cc/paper_files/paper/2024/file/9ddc141bdbf9d1db510cefff56c586ad-Paper-Conference.pdf#page=19)

### What changes when someone else diagnoses the failure

In §4.2, Code Llama repaired with feedback from GPT-3.5 or GPT-4 on HumanEval. On APPS, the tested pairs were Code Llama with GPT-3.5 feedback and GPT-3.5 with GPT-4 feedback. The programming model for each pair continued to generate and repair the code, with one separately generated diagnosis and one repair per failed starting point. The tested pairings improved on their programming model's fresh-only and same-model repair curves under candidate-count accounting. Appendix A checks the broad pattern with generated-token accounting. The gain supports the authors' feedback-bottleneck hypothesis. The switch also changes joint versus separate prompting, and this study offers no matched literal-error-only repair arm for estimating the added value of same-model natural-language diagnosis over a test error by itself. It also does not price the separate stronger model call or compare the arrangement at equal dollar cost with simply using the stronger model as programmer. [Conference PDF, §§3.1, 4.2, Fig. 5 and App. A, Figs. 8 and 11](https://proceedings.iclr.cc/paper_files/paper/2024/file/9ddc141bdbf9d1db510cefff56c586ad-Paper-Conference.pdf#page=8)

The human experiment starts later in the workflow. Two failing GPT-4 solutions were selected for each of 20 APPS tasks, deliberately weighted toward introductory tasks (14 introductory, three interview, three competition). Sixteen participants, 15 graduate students and one professional machine-learning engineer, each saw five programs. Two people commented on each original program. They had the task, failing code, execution evidence and two GPT-4 diagnoses with the repair code removed. In the outcome comparison GPT-4 generated 25 repair candidates for each of two model diagnoses and each of two human-written diagnoses per program. Of 2,000 repair candidates per feedback condition, 33.30% passed with GPT-4 feedback and 52.60% with the human-written feedback, a 19.30 percentage-point increase. These candidate outcomes share diagnoses, programs and tasks. Appendix E shows large within-task differences as well as stubborn failures. All sampled repairs for both versions of task 2923 failed in both feedback conditions. These results describe the effect of supplying the human-written diagnoses on the selected failures, with assistance available to the humans while preparing their feedback. Human debugging time and end-to-end developer productivity were outside the measurement. [Conference PDF, §4.3, Table 1, pp. 8–9, §5, p. 9 and Apps. D–E, pp. 24–26](https://proceedings.iclr.cc/paper_files/paper/2024/file/9ddc141bdbf9d1db510cefff56c586ad-Paper-Conference.pdf#page=8)

The authors manually judged 32 of 80 GPT-4 explanations and seven of 80 human explanations obviously inaccurate. They categorize more GPT-4 feedback as suggesting small edits and observe expressed uncertainty in seven human responses and zero model responses in this sample. Only two human responses supplied code or pseudocode blocks. Appendix F illustrates the difference between changing a line and diagnosing a mistaken approach: one participant identifies why choosing a shortest path would not solve a graph-separation problem, then suggests checking a cut formulation. The annotations are descriptive judgments. The study did not independently vary the size of the recommendation or its expression of uncertainty, so their individual effects on repair are unknown. [Conference PDF, §4.3, pp. 8–9, and App. F, including §§F.3 and F.5](https://proceedings.iclr.cc/paper_files/paper/2024/file/9ddc141bdbf9d1db510cefff56c586ad-Paper-Conference.pdf#page=9)

## Extractable practitioner insights

### BP-04 Feedback flip

When the tool keeps proposing fixes for a reproducible failure, there is value in examining the explanation itself. The paper tests the chain from execution evidence to diagnosis to patch. A practitioner adaptation is to ask for the violated behavior and its connection to the code, check that diagnosis against a reproducing case, then have the model revise and rerun the original tests. Escalate diagnosis to an appropriately informed human or stronger model if the explanation cannot account for the failure or the original approach conflicts with the specification. Same-model role-switching, a review-only prompt, independent model review without test evidence and in-session patch authoring are distinct practitioner interventions whose effects this experiment did not isolate. The empirical result is stronger for feedback that improves test-passing repairs than for a generic instruction to critique previous output. Claims SRC-0008:C01, C08–C11. [Conference PDF, §§3.1, 4.2–4.3 and 5](https://proceedings.iclr.cc/paper_files/paper/2024/file/9ddc141bdbf9d1db510cefff56c586ad-Paper-Conference.pdf#page=8)

### BP-08 Parallel implementations, with supporting BP-03 and AP-01 evidence

When several small, independently testable implementations are cheap to produce, keep fresh attempts available as a comparison for further repair. An original adaptation is to give each fresh attempt the same requirements and fit each candidate to the same behavioral tests, then spend a bounded amount of repair effort on a candidate with a well-understood failure. Use the team's ordinary review criteria when several candidates pass. The experiment supports trying fresh alternatives under a budget and checking them, with results contingent on a dependable test oracle. It does not establish that simultaneous execution saves wall-clock time, that a human or AI can pick the best of several plausible patches without dependable tests, or that concurrent agents produce meaningfully different designs. It provides a plausible benchmark basis for abandoning an unproductive initial solution. It does not identify a general repair-turn cutoff or measure the cost of reverting a live repository change. Claims SRC-0008:C02, C05–C07 and C11. [Conference PDF, §§3.2, 4.1, 5 and App. A](https://proceedings.iclr.cc/paper_files/paper/2024/file/9ddc141bdbf9d1db510cefff56c586ad-Paper-Conference.pdf#page=6)

### OB-06 Non-determinism

This is supporting evidence that additional stochastic draws from the same coding model are worth considering where a fixed-specification task has an objective check. It measures benchmark pass rates under repeated sampling at temperature 0.8. It does not quantify identical-prompt output disagreement, compare decoding temperatures, isolate infrastructure-level nondeterminism, or test how repeated dialogue changes convergence. A seed, temperature, model version and test suite together matter when comparing actual runs. Claims SRC-0008:C02, C04–C06. [Conference PDF, §§3.2 and 4](https://proceedings.iclr.cc/paper_files/paper/2024/file/9ddc141bdbf9d1db510cefff56c586ad-Paper-Conference.pdf#page=5)

## Related work, conflicts, and limitations

Adnan and Kuhn's later [source dossier](SRC-0003--debugging-effectiveness-decay.md) offers a distinct empirical comparison on HumanEval. Their Table 2 tests spending a later slot in a sequential debugging chain on a fresh start at one of two model-specific thresholds, with a shared six-attempt cap and continuous repair as the baseline. Their effectiveness metric tracks the incremental rescue rate among still-unsolved tasks at each step. Olausson et al. compare a tree's any-pass rate with an entirely fresh sample budget and allow several starting points. Their sequential token variant walks the same tree in a different order. Its repair alternatives still take the same initial program as input. The results are compatible with the broad trade-off between working on the current candidate and drawing a new one. They use shared HumanEval tasks, different experiments and outcome definitions, and neither validates the other's allocation or identifies a general causal effect of accumulated chat history. Olausson et al.'s APPS results extend the budget comparison to another benchmark of self-contained Python tasks. Claims SRC-0008:C02, C05–C07 and SRC-0003:C03, C06–C08. [Adnan and Kuhn, RQ3, Debugging protocol and Table 2](https://www.nature.com/articles/s41598-025-27846-5?code=7b2&error=cookies_not_supported) · [Olausson et al., §3.2 and App. A](https://proceedings.iclr.cc/paper_files/paper/2024/file/9ddc141bdbf9d1db510cefff56c586ad-Paper-Conference.pdf#page=4)

The tested endpoints, precomputed sample pool, prompt exemplars and benchmark test suites bound the effect sizes. The papers' overlapping observations do not estimate how much context to retain in a repository, which test suite is adequate for merging a change, or whether several competing branches repay review and integration time. [Conference PDF, §5 and App. G](https://proceedings.iclr.cc/paper_files/paper/2024/file/9ddc141bdbf9d1db510cefff56c586ad-Paper-Conference.pdf#page=9)
